# Agent-readiness review

*Audit of the repository at `9bd598f` (2026-09-25) from the point of view of an
autonomous client — Claude Code, Codex, Cursor or any HTTP/MCP-capable agent —
trying to operate AIDRA without a human in the loop. Every gap cites the code
that causes it.*

## Product summary

AIDRA is an **evaluation study, not an operational service**: it answers
"can AI vessel detection on Sentinel-1 radar run on satellite-class hardware,
and how much quality does it lose?". It does that with a real, deployed
pipeline:

1. search and download a Sentinel-1 GRD scene from Copernicus for a named sea
   area ("zone"),
2. calibrate, speckle-filter and tile it,
3. detect vessels with a CFAR + YOLOv8 ensemble while a **constraint profile**
   (`ground` … `sat-extreme`) caps the CPU and RAM budget to emulate on-board
   processors,
4. persist every detection in PostGIS with its full provenance (SHA256 of image,
   model and output, parameter hash, commit SHA),
5. publish results as GeoJSON, STAC and OGC API Features, and
6. evaluate model variants (FP32 vs INT8) against labelled xView3-SAR scenes
   and against each profile — the "compression triplet".

A Tip & Cue loop queues re-observations of areas where high-confidence
detections cluster. Everything runs on one OCI ARM box (4 OCPU, 24 GB) with
Grafana, Prometheus and Loki beside it.

**Current human users**

| User | What they do | Through |
|---|---|---|
| Operator / researcher (the owner) | Trigger runs, import validation reports, fetch weights, build evidence bundles, diagnose failures | `curl`, ad-hoc scripts outside the repo, Grafana's SQL datasource proxy, the Coolify API |
| Evaluator / reviewer | Judge methodology and evidence (Pd, FAR, ΔmAP, latency per profile) | Grafana dashboards, `EVIDENCE.md`, `reports/*.md` |
| GEOINT analyst | Pull detections into QGIS / EODAG / pystac-client | GeoJSON, STAC, OGC API Features |

## Existing agent-accessible capabilities

The product is already API-first — the no-SSH rule made every operational task
an HTTP call. What an agent can use today:

| Surface | What it covers | Notes |
|---|---|---|
| REST under `/api` (≈50 routes, `src/api/`) | Health, pipeline trigger/status/reset, detections (list, GeoJSON, by id, thumbnail), traceability per execution, D3 bundle build, benchmarks, models/profiles/zones, Tip & Cue queue + manual cue, validation runs (synthetic, import, list), interpretability runs, orbital simulations | Writes need `Authorization: Bearer $AIDRA_API_TOKEN`; reads are public |
| OpenAPI 3 | `/openapi.json`, `/docs` generated by FastAPI | Coverage is uneven (see gaps) |
| STAC 1.0 + OGC API Features Part 1 | `/api/stac/*`, `/api/ogc/*` — standard, paginated, `links[rel=next]` | The most machine-friendly part of the API; built for GIS clients |
| Prometheus | `/api/metrics` with `run_id` exemplars | Metrics, not answers |
| CLIs | `python -m src.traceability {verify,bundle,verify-bundle}`, `scripts/run_validation.py`, `scripts/validate_xview3_serial.py`, … | Need a local checkout, the heavy ML stack and often direct DB access |
| Claude Code config (`.claude/agents`, `.claude/commands`) | Subagents and slash commands for *developing* the repo | Aimed at coding agents working on the source, not at operating the product |

## Human-only capabilities

Important questions that today need a UI, a private credential or tribal
knowledge:

1. **"What ran recently, and what failed?"** There is no route that lists
   executions. `SELECT_EXECUTIONS` exists in `src/db/queries.py:48` but only
   `ExecutionRecorder.list` uses it; no endpoint does. STAC items only show
   `status='success'` (`src/api/stac.py:227`). The operator answers this with
   Grafana panels or raw SQL through Grafana's datasource proxy (admin password).
2. **"Why did it fail?"** The failure signal sits in `execution_log.status`,
   `error_message` and `notes` (e.g. the memory-budget abort, the reaper's
   `reaped: stuck in running…`, the dedup `skipped: scene … already processed`).
   An agent can only read those fields if it already knows the execution id,
   and nothing tells it what each status means.
3. **"What configuration is production actually running?"** The effective
   `Settings` (CFAR window, fusion mode, thresholds, band streaming) live in
   Coolify env vars. The project already tripped on this — the CFAR window
   could differ from `.env.example` without anyone noticing. There is no
   read-only config endpoint; the operator reads it through the Coolify API
   with a root token.
4. **"Is the INT8 variant good enough?"** The compression-triplet verdict
   (I-MOD-1/2/3: baseline + variant + profile, ΔmAP ≤ 5 pts) is assembled by
   hand from `reports/*.md`, `GET /api/validation/runs` and `GET /api/benchmarks`.
   No endpoint computes it.
5. **"Which model variants may I use?"** Registry status (`active`,
   `candidate`, `rejected` with `rejection_reason`) is in the table
   (migrations 015/019/020) but `GET /api/models` drops it (`ModelInfo`,
   `src/db/models.py:111`). Live, the API lists the rejected `int8-dynamic`
   variant and a COCO `yolov8n` that the SAR gate refuses at run time —
   indistinguishable from the good ones.
6. **Multi-step operations** (triplet runs, post-deploy imports) are driven by
   scratch scripts that are not in the repository.

## Agent-readiness gaps

Ordered by how badly they break an autonomous client.

### A. Wrong or invisible state

- **`GET /api/pipeline/status` only knows about API-triggered runs.** It reads
  an in-memory dict (`src/api/pipeline.py:35`). Scheduled scans and Tip & Cue
  runs call `engine.run()` directly (`src/pipeline/scheduler_jobs.py:236`,
  `:277`), so status says `running: false` while a 50-minute run is on the box.
  `progress` is a constant (`0.1`, then `1.0`).
- **The concurrency guard has the same blind spot.** `POST /pipeline/trigger`
  only checks the in-memory flag, so an agent can start a second full-scene run
  on top of a scheduled one — on a host whose RAM budget is the object of study.
- **An `execution_id` can be returned for a run that never exists.** The
  trigger returns `status: started` with a fresh UUID before the zone or the
  model are validated. If `_validate_request` or `get_model` fails — unknown
  zone, ambiguous model, missing card, COCO model on SAR — it fails *before*
  `create_pending` (`src/pipeline/engine.py:330-380`), so no row is ever
  written and `GET /api/traceability/{id}` returns 404 forever. The agent can't
  tell "not created yet" from "rejected".
- **STAC links to data that isn't there.** Each STAC item's
  `thumbnail_gallery` asset points at `/api/detections?execution_id=…`
  (`src/api/stac.py:319`), but `GET /api/detections` has no `execution_id`
  parameter. FastAPI ignores it and returns the global top-confidence list, so
  an agent following the link reads another scene's detections as this one's.

### B. Missing discoverability

- Enumerations are prose, not schema: execution status (`pending`, `running`,
  `success`, `error`, `skipped`, `invalid`, `oom`, `failed`), `quality_verdict`,
  `trigger_type` and cue `status` are plain `str` in OpenAPI. The tasking
  description says `executing`; the real value is `processing`
  (`src/db/queries.py:359`).
- Two zone vocabularies, and nothing maps one to the other: pipeline search
  zones (`gibraltar`, …) and Tip & Cue zones (`gibraltar_strait`,
  `algeciras_port`, …; `src/tipcue/zones.py`). Cue rows show the second kind,
  but the trigger only accepts the first.
- The catalogs exist twice. `src/api/models_api.py:33` and `:80` copy
  `src/profiles/definitions.py` and `src/pipeline/ingestion.py:65` by hand, so
  what the API advertises can drift from what the engine accepts.
- Query examples in descriptions name models that don't exist (`yolov8n-sar`,
  `yolov8n-sar-int8` in `src/api/benchmarks.py:46`,
  `src/api/detections.py:135`).

### C. Responses shaped for a dashboard, not a reader

- `GET /api/traceability/{id}` returns *every* detection of the execution,
  unpaginated (`src/api/traceability.py:30`). A production run holds
  hundreds to thousands, so one call can fill an agent's context window.
- `GET /api/detections/{id}` returns a flat 60-column joined row that
  includes the server's `thumbnail_path`.
- `GET /api/detections` sorts by confidence across **652 029** rows that repeat
  the same vessel once per profile and once per re-run of a scene (the live API
  returns the same box twice, from executions `d5d3f3f6` and `14a3ff48`). An
  agent counting vessels in an area over-counts, and nothing warns it.
- No response says what to do next (the id to poll, the valid values, the
  follow-up endpoint).

### D. Errors that don't steer the agent

- Mixed error shapes: `detail` is sometimes a string and sometimes a dict. There
  is no machine-readable error code, so the agent can't tell "retry later" from
  "fix your input" from "you lack permission".
- `400` and `422` are used interchangeably for bad input.
- Most 500s echo the raw exception (`f"Failed to query detections: {exc}"`),
  which leaks internals and still doesn't say what went wrong.
- Valid values are returned for an unknown profile (`src/api/pipeline.py:218`)
  but not for an unknown zone, model or status.

### E. Retries and safety

- **Not safe to retry.** `POST /api/tasking/cue` inserts a duplicate on every
  retry. `POST /api/pipeline/trigger` either returns 409 or, if the first run
  already finished, starts a second one — manual runs skip the dedup on purpose
  (`engine.py:1124`). There is no `Idempotency-Key`.
- **No preview.** A run costs a ~1.7 GB download plus 6–52 minutes of the
  box's only CPU budget. Nothing tells the caller in advance which model
  version, thresholds and profile will actually be used, or whether the run
  collides with another.
- **One all-powerful secret.** A single `AIDRA_API_TOKEN` authorises every
  write (`src/main.py:295`), from queuing a cue to overwriting model weights
  (`POST /api/models/fetch` with `overwrite=true`). You can't hand an agent
  "may launch runs" without also handing it "may replace the weights the
  evidence was produced with".
- **Unconfined write paths.** `POST /api/traceability/bundle` and
  `POST /api/interpretability/run` accept any `out_dir` and write there
  (`src/api/traceability.py:152`, `src/api/interpretability.py:36`).
- **A read endpoint that needs the write token.** The global write middleware
  requires the token on every non-GET `/api` route, including the read-only
  `POST /api/stac/search`. STAC clients that search by POST get 401 in
  production.

### F. Missing audit trail for API actions

`execution_log` records *what ran* with excellent provenance, but nothing
records *who asked*. Mutating calls leave only an INFO log line (most leave
nothing). Nobody can answer "what did the agent do today?", "which call
created this cue?" or "why was this request rejected?" after the fact.

### G. Documentation for machines

- There is no `AGENTS.md`. `CLAUDE.md` is a Spanish contract for coding agents
  editing the repo, not for agents operating the product.
- OpenAPI mixes Spanish and English. About a third of the routes return a bare
  `dict` with no response model, and no route carries an example.
- The invariants that decide how data should be read (I-DET-2: land artefacts
  kept but excluded from sea metrics; `tier=high` is an operating point, not a
  filter; union vs fused) live only in `CLAUDE.md` and the README.

### Found later, during implementation

The code reading above missed these. They surfaced once the interface ran
against a real database:

- **Every bbox query returned 500 in production.** `GET /api/detections?bbox=…`,
  `/detections.geojson?bbox=…` and `/ogc/collections/detections/items?bbox=…` all
  failed with `function st_intersects(geometry, text) is not unique`. The
  string-replace that swaps in `ST_GeomFromGeoJSON` cast only the first of two `$n`
  occurrences. The mocked-DB API tests can't see SQL typing, so it went unnoticed.
  The `count_gibraltar_week` eval caught it on its first run.
- **The AI Act card gate had a side door.** `ModelManager.get_model` loaded a weight
  that had no registry row straight from its file, without checking the card
  (I-AIA-1). An unregistered file usually means registration failed *at* the card
  gate.
- **A Tip & Cue zone that can't see itself.** `med_patrol` (lon 10–16) maps to the
  `mediterranean_west` search zone (lon −1–4). Its cues re-observe scenes that don't
  cover it.
- **Known-bad configurations are re-runnable blind.** Nothing warned that the last
  INT8 run on `sat-mid` had aborted on its memory budget, so another attempt would
  spend 1.7 GB of download to reproduce it.

### What is already good (keep it)

- Provenance is excellent. Every run carries `image_hash`, `model_hash`,
  `output_hash`, `input_params_hash` and `commit_sha`, and the pending row is
  written before the run (I-TRACE-2).
- Standards-based read APIs (STAC, OGC Features) with real pagination links.
- The no-SSH rule already turned every operational task into an HTTP call.
- Safety rules already live in the domain: the AI Act card gate (`ModelManager`
  refuses weights without a `MODEL_CARD.md`), SHA256-pinned model fetch,
  "mark, don't delete" for rejected variants and failed runs, and a guarded
  `/pipeline/reset` that refuses while the DB says a run is live.
- Structured JSON logs with `execution_id`, shipped to Loki, and Prometheus
  exemplars that link a metric spike back to its run.
